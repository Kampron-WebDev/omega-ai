## System Boundaries

- `app/api` — Authenticated request handlers: input validation, access checks, task triggering, and persistence. They never call an LLM.
- `trigger` — Long-running background jobs: design generation, spec generation, review, build plans, and the stale-run reaper.
- `lib` — Shared infrastructure: Prisma client, access control, env, canvas schema and layout, room access, Blob artifacts, and AI prompts (`lib/ai/`).
- `types` — Shared contracts: canvas types, realtime feed schemas (`types/tasks.ts`), review and build plan schemas.
- `components` — UI composition: canvas surfaces, sidebars, dialogs, and interactive elements. No business logic.
- `hooks` — Client state and effects (autosave, AI status and run, specs).
- `prisma` — Database schema. Folder-based: `prisma/schema.prisma` holds the generator and datasource blocks, `prisma/models/*.prisma` hold the models, `prisma/migrations` holds migration history.
- `generated/prisma` — Generated Prisma Client (TypeScript sources). Build output, gitignored, regenerated by `postinstall`. Never edited, and never imported outside `lib/prisma.ts`.
- `prisma7.config.ts` — Prisma 7 CLI config at the repo root: schema location, migrations path, and the datasource URL. Prisma 7 does not read `.env*` on its own, so this file loads `.env.local` then `.env` to match Next.js.
- `data` — Legacy local directory. Not used for new artifacts.

## Storage Model

- **Database:** metadata, ownership, relationships, task runs, and artifact references.
- **Liveblocks Storage:** the live canvas (the default `useLiveblocksFlow` key) and the project brief (`brief`, planned: spec 28). This is the source of truth while people are editing.
- **Liveblocks Feeds:** `ai-chat` (room conversation) and `ai-status-feed` (AI run status). Planned: specs 29–30.
- **Vercel Blob:** durable artifacts, always written by the server. Blob URLs are stored in the database and never sent to the browser.

| Artifact | Blob key | Database reference |
| --- | --- | --- |
| Canvas snapshot (autosave) | `canvas/{projectId}/{random}.json` | `Project.canvasJsonPath` |
| Checkpoint | `checkpoints/{projectId}/{random}.json` | `CanvasCheckpoint.blobUrl` |
| Technical spec | `specs/{projectId}/{random}.md` | `ProjectSpec.filePath` |
| Architecture review | `reviews/{projectId}/{random}.json` | `ArchitectureReview.filePath` |
| Build plan | `plans/{projectId}/{random}.json` | `BuildPlan.filePath` |

Snapshot format: `{ schemaVersion, savedAt, nodes, edges, brief? }`. Version 1 has no brief; version 2 (spec 28) adds it. Readers accept every version.

## Auth and Collaboration Model

- Every project has a single owner (Clerk user ID).
- Projects can include additional collaborators, addressed by normalized email.
- Only authenticated users can access protected routes.
- Page routes are gated in `proxy.ts`. `app/api` routes authenticate inside each handler instead, so they can answer `401`/`403` as JSON rather than the `404` Clerk's `auth.protect()` returns for non-page requests. Spec 44 moves page routes to resource-level checks as well.
- Only the owner or a collaborator (a *member*) can read or mutate project resources. Rename, delete, and sharing are owner-only.
- Liveblocks room tokens are issued only after verifying project membership. The room ID is the project ID.
- Personal access tokens (spec 45) resolve to the same identity as a session, and are read-only.

## Starter System Designs

- Prebuilt templates are static canvas snapshots stored in the codebase.
- Templates are loaded into the active Liveblocks room when a user imports one. From spec 26, importing over a non-empty canvas checkpoints first.
- Import can occur on canvas creation or from within the editor at any time.
- Template data follows the same node/edge schema as user-created canvas content, and is validated by `lib/canvas-schema.ts` in a test.
- Templates do not require a separate database record; they are resolved by template ID at import time.

## AI Generation Model

### Common to every AI task

- Started by a route through `lib/trigger-runs.ts`, which enforces rate limits and **one active run per project**, and records a `TaskRun`.
- Context is read **on the server** from the room (graph, brief, chat, open comment threads). A graph, a chat history, or a project ID from the client is never trusted.
- All user-authored content in prompts is fenced as untrusted data.
- Model output is validated with zod. One repair attempt, then the run fails.
- Progress goes to `ai-status-feed`, replies go to `ai-chat`, and AI presence appears as the Liveblocks user `omega-ai`.
- Failures publish a safe message and always clear presence. The stale-run reaper cleans up runs whose worker died.

### Design Generation

- Input: user prompt, brief, current canvas, and recent chat.
- Execution: `trigger/design-agent.ts`.
- Output: a typed operation plan, validated and applied by the pure function `applyDesignPlan`. Positions come from `lib/canvas-layout.ts`, never from the model. The plan is written with `mutateFlow` after an `AI_RUN` checkpoint.

### Spec Generation

- Input: canvas graph, brief, chat, and open threads.
- Execution: `trigger/generate-spec.ts`.
- Output: Markdown combining deterministic sections (Mermaid diagram, component and connection tables) with model-written sections. Saved to Blob and linked through `ProjectSpec`.

### Review and Build Plan

- Review: deterministic lint (`lib/architecture-lint.ts`) plus AI findings, linked to node and edge IDs.
- Build plan: ordered implementation units in this repository's spec format, plus context documents. They are assembled into the agent pack without further LLM calls.

## Invariants

1. Request handlers do not run long-lived or AI work — that belongs in background tasks.
2. Metadata and large generated artifacts are stored in separate layers.
3. Auth and access are enforced at every read and mutation boundary. Personal access tokens never mutate.
4. Client components are used only where browser interactivity or real-time state requires them.
5. The canvas schema is the same for user-created content, templates, snapshots, imports, and AI output, and `lib/canvas-schema.ts` is its only validator.
6. No model output reaches the canvas, the database, or Blob without schema validation.
7. Every AI change to the canvas is preceded by a checkpoint.
8. The server is the only writer of Blob artifacts. Blob URLs never reach the browser.
