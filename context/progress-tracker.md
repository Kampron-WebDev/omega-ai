## Architecture Decisions

- **`GET /api/projects` returns both lists**, `{ owned, shared }`, not a single flat list. Spec 06 says "the current user's projects" and spec 07 needs owned *and* shared from "the existing project data helper"; one shape satisfies both. `lib/projects.ts` is that helper and is the only reader — the route is a thin wrapper over it, so spec 07's Server Component can call `listProjectsForIdentity()` directly instead of fetching its own route.
- **`slug` is derived from the current name in the API response, never stored.** It matches `types/project.ts`'s `Project` exactly (`id`, `name`, `slug`, `role`), so wiring the sidebar in spec 07 is a swap of the data source and nothing else. This follows from the room-ID decision: the cuid is identity, the name is the label, the slug is a rendering of the label.
- **`/api/(.*)` is excluded from `auth.protect()` in `proxy.ts`.** Clerk's `protect()` answers a non-page request with `404` (`node_modules/@clerk/nextjs/dist/esm/server/protect.js`: page → redirect, Server Action → 401, everything else → `notFound()`), so with the middleware in front, every unauthenticated API call would have surfaced as a missing route instead of spec 06's required `401`. Each handler authenticates itself, which is also the migration target for the `createRouteMatcher` deprecation; the middleware keeps protecting page routes.
- **Ownership failures distinguish 404 from 403 by existence, not by visibility.** `findOwnedProject()` returns `not_found` for an unknown ID and `forbidden` for a real project owned by someone else, so a non-owner can confirm a project ID exists. Spec 06 mandates `403` for non-owner mutations, which requires exactly this; revisit if project IDs ever need to be unguessable.
- **Request validation is hand-rolled in `lib/project-input.ts` rather than using `zod`.** `zod` is present in `node_modules` only as a transitive dependency of `eslint-config-next` and `shadcn`, at two different major versions — importing it would be an undeclared dependency resolved by hoisting luck. The only input these routes take is an optional `name` string.

- `ProjectSidebar` is `position: fixed`, anchored `top-12` (matching the navbar's `h-12`) so it overlays the canvas below the navbar without pushing layout, per the "should not push page content" requirement.
- Auth route protection uses a protected-first `proxy.ts` strategy (block everything, allow-list `/`, `/sign-in(.*)`, `/sign-up(.*)`) rather than public-first, matching `architecture-context.md`'s "Only authenticated users can access protected routes" invariant and the spec's "Protect everything else by default." Narrowed in spec 06 to page routes only — see the `/api/(.*)` exclusion above.
- `/` owns its own redirect logic at the page level (Server Component + `auth()`) rather than relying on the proxy's default `auth.protect()` redirect, since the spec calls out `/`'s authenticated/unauthenticated behavior as a distinct requirement; `/` is in the proxy's public allow-list so this logic isn't shadowed.

- Project mutations flow through a single `ProjectDialogIntent` union (`create` / `rename` / `delete`) emitted by `useProjectDialogs`, rather than three separate callbacks. The editor currently hands it to `useMockProjects`; the persistence chapter swaps that one callback for an API call without touching the hook or any dialog.
- `slugify` lives in `lib/` rather than inside the create dialog, because `architecture-context.md` requires ownership/validation at the mutation boundary — the server will need to derive the identical slug from the same name.
- Sidebar row actions are inline hover/focus-revealed icon buttons instead of a dropdown menu: only two actions exist, it avoids a popup nested inside the sidebar overlay, and it needs no new `components/ui/*` file (protected per `ai-workflow-rules.md`). Tailwind v4 scopes `group-hover` behind `@media (hover:hover)`, so an explicit `@media (hover:none)` rule keeps the actions permanently visible on touch devices.
- Owner-only actions are gated inside `ProjectListItem` on `project.role === "owner"` rather than by which list rendered the row, so the rule holds wherever a project row is reused later.

- No headless browser tooling is installed, so the project dialogs were verified by build + prerendered-HTML grep + a compiled `slugify` check rather than by clicking through them. Dialog open/close, focus behavior, and the mobile scrim have not been exercised in a real browser.

- The Prisma schema is folder-based (`schema: "prisma"` in `prisma7.config.ts`), per the spec's `prisma/models/project.prisma` path. The generated client is written to `generated/prisma` at the repo root rather than inside `prisma/`, because a folder-based schema recursively globs `*.prisma` under the schema directory and generated output there can collide with schema discovery.
- Prisma 7 requires a driver adapter and does not read `.env*` files. `prisma7.config.ts` (the Prisma 7 filename; plain `prisma.config.ts` is the legacy name and is only searched as a fallback) loads `.env.local` then `.env` via `dotenv` so the CLI and the Next.js runtime resolve the same `DATABASE_URL` from one file.
- `lib/prisma.ts` throws on a missing `DATABASE_URL` inside the client factory rather than returning a lazily-failing client, so a misconfigured environment fails at startup with a named error instead of surfacing as an opaque query failure inside a request handler.
- **The Liveblocks room ID is the `Project` cuid.** No `roomId` column, no slug-derived identifier. Spec 10 ("use the project ID as the Liveblocks room ID") and spec 07 ("the project ID and Liveblocks room ID should stay aligned") both point here; spec 07's other clause, "slugify the name to create the room ID", is the outlier and is not followed. The deciding factor is rename: spec 06 ships `PATCH /api/projects/[projectId]`, and a name-derived room ID makes rename either a lie (identifier frozen at creation, drifting from the name) or a distributed data migration (the canvas lives *inside* the Liveblocks room, which cannot be renamed in place — new room, copy storage, disconnect every client, strand every shared link). With the cuid, rename is one `UPDATE` on a text column. Identity (immutable cuid), label (mutable `name`), and locator (an optional future slug) stay separate. This is also the reversible direction: cuid → pretty URLs later is a nullable column plus a redirect, while slug → cuid would have to move canvas state between rooms. Consequences for spec 07: drop the "short unique suffix", drop the create dialog's room ID preview (a cuid cannot be previewed before insert), and keep spec 04's `slugPreview` only as a display label. Access resolution in specs 08 and 27 becomes a primary-key lookup.
