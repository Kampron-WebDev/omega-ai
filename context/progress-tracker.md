## Architecture Decisions

- **Specs 21–29 were rewritten and renumbered into a 21–46 roadmap (2026-09-28).** The old order had real dependency bugs. For example, the design agent (old 23) published to a status feed whose schema came one spec later (old 24), and the chat spec (old 26) posted the AI's final reply from the requester's browser, so it was lost whenever that tab closed. Mapping from old to new: autosave 21→25, design API 22→31, design logic 23→33, AI presence 24→29, chat feed 25→30, chat functional 26→32, spec flow 27→35, spec persistence 28→36, spec UI 29→37. The rewrites also change these behaviors:
  - AI and spec tasks read the graph, brief, and chat from the room on the server instead of accepting them from the client.
  - Autosave is server-written: the client only signals, and the server reads the room.
  - The AI proposes typed operations; placement comes from a layout engine, never model coordinates.
  - One active AI run per project.
  - A single generic run-token route replaces the per-feature token routes.
  - Spec 32 keeps the spec 20 tokens instead of the old green hex.

  New specs add a test and CI foundation, semantic node kinds, an inspector, checkpoints, auto-layout, the project brief, guardrails, architecture review, build plans, the agent pack, export and import, comments, a command palette, hardening, access tokens, and an MCP server. `context/feature-specs/README.md` holds the roadmap and conventions.

- **Spec 20's color names are mapped onto the tokens that exist; no new tokens were added.** The spec's class names come from a different token set. Mapping: `bg-base` → `bg-bg-base`, `bg-elevated` → `bg-bg-elevated`, `bg-subtle` → `bg-bg-subtle`, `border-surface-border` → `border-border-default`, `text-primary-text` → `text-copy-primary`, `text-muted-text` → `text-copy-muted`, `bg-brand-dim` → `bg-accent-dim`. "Accent" (`bg-accent`, `text-accent`, `text-accent-text`) maps to the AI accent (`bg-ai`, `text-ai-text`), not to this project's `bg-accent`: here `accent` is shadcn's slot and resolves to the 12% cyan brand dim, so `bg-accent text-white` would be white text on a near-transparent tint, and `ui-context.md` defines `--accent-ai`/`--accent-ai-text` as exactly the accent/accent-text pair for AI surfaces. The old spec 26 asked for green (`#62C073`) bubbles and send button, a hex from the node palette rather than a token. Its rewrite (spec 32) keeps these tokens instead.
- **The AI sidebar floats below the canvas presence pill.** Spec 20 says to keep the existing "floating position" and "slide animation", but the placeholder it replaced was an inline, conditionally rendered column with neither. The panel follows `ui-context.md`'s "slide-over AI sidebar on the right" instead, and starts at `top-28` so it clears the presence pill (`top-4`, 36px tall, inside the canvas below the 48px navbar) — the user's `UserButton` stays reachable while the panel is open. It overlays the right edge of the canvas rather than narrowing it.

- **Template import is one Liveblocks batch.** Clearing the canvas and adding the template run inside a single `room.batch`, so collaborators receive the swap as one update (never an empty canvas in between) and one undo restores the previous canvas. Batches nest, so `useLiveblocksFlow`'s own mutations fold into it.
- **The canvas is driven from the navbar through an imperative handle, not lifted state.** The navbar lives outside `RoomProvider`, and moving the room boundary up would change the collaborative setup spec 18 says to leave alone. `CanvasFlow` exposes `importTemplate` via `useImperativeHandle`; the handle is `null` until storage loads, so an import before the canvas connects does nothing.

- **The shortcuts hook is `hooks/use-keyboard-shortcuts.ts`, not `hooks/useKeyboardShortcuts.ts`.** Spec 17 names the hook `useKeyboardShortcuts`, and the export keeps that name; the file follows the kebab-case `use-*.ts` convention every other file in `hooks/` already uses.
- **"Sit above the shape panel" is read as stacking order.** Spec 17 also places the bar at the bottom-left while the shape panel is bottom-center, so the two share the bottom edge; the bar's `z-10` keeps it on top where they meet on narrow viewports.

- **Edge labels live in `edge.data.label`, not React Flow's top-level `edge.label`.** Liveblocks' `EDGE_BASE_CONFIG` syncs top-level `label` as an atomic value, while `data` is left to the app and synced as a nested `LiveObject` — the same place node labels live. Keeping labels in `data` makes `updateEdgeData` a line-for-line mirror of `updateNodeData` and leaves room for future per-field edge data without write conflicts.
- **Edge labels commit on finish, node labels commit per keystroke.** Spec 16 says to save on blur, Enter, or Escape, so the edge input holds a local draft; spec 14's node editor writes through on every change. Escape saves rather than cancels, per the spec's wording.

- **The workspace answers "missing" and "forbidden" identically.** `findProjectForIdentity()` returns `null` for both, and `/editor/[roomId]` renders the same `AccessDenied` either way. That is spec 08's requirement read literally, and it also means the page cannot be used to enumerate project IDs — the opposite trade-off from `PATCH`/`DELETE`, which spec 06 requires to answer `403` distinctly. The difference is deliberate: the mutation routes are owner-only and already know the caller has an ID in hand, the workspace URL is guessable.
- **The Share button ships rendered but disabled.** Spec 08 lists it as a navbar action and simultaneously forbids sharing behavior. A button that silently does nothing is worse than one that says it is not ready, so it carries `disabled` until spec 09 wires it.

- **`POST /api/liveblocks-auth` returns `403`, not the workspace's indistinguishable `404`, for a project the caller cannot access.** Spec 10 states this explicitly ("Return 403 for unauthorized project access"), and it does not weaken the existence-hiding the workspace route relies on: this endpoint is only ever called by a client already trying to open a specific room ID it already has, not one guessing IDs, so confirming that ID is a real project reveals nothing new.
- **`liveblocks.config.ts` declares `Presence` and `UserMeta` as `type` aliases, not `interface`s.** Discovered wiring `RoomProvider` in spec 11: its `initialPresence` prop requires `Presence extends JsonObject` (`{ [key: string]: Json | undefined }`), and TypeScript only resolves that structural check for a plain object type — an `interface` with identical members failed it, surfacing as `GetOverride`'s "is not a valid JSON object" error the moment a real generic consumer (`RoomProvider`) checked it. This was a latent bug in spec 10, invisible because nothing in that unit's scope instantiated `RoomProvider` or `useLiveblocksFlow` against the augmented type. The `declare global { interface Liveblocks { Presence: Presence; UserMeta: UserMeta } }` augmentation block itself is unaffected — only the two type definitions being merged into it changed shape.
- **`liveblocks.config.ts` names the thinking-indicator presence field `thinking`, not spec 10's literal `isThinking`.** Specs 19 and 24 both define presence with `thinking`, spec 10 is implemented first, and one shared type has to pick a single name — this was flagged as an open question before spec 10 existed and is resolved by taking the name the later specs (which outnumber spec 10) already agree on.

- **`useProjectActions` wraps `useProjectDialogs`; it does not replace it.** Spec 07 asks for a hook that "manages dialog state and project mutations", and spec 04 already built the dialog-state half behind an `onSubmit` seam. The new hook supplies that callback and returns the same `ProjectDialogsController`, so swapping mock data for the API touched no dialog and no sidebar — which is what the seam was for.
- **Reads bypass the route; mutations go through it.** `app/editor/page.tsx` calls `listProjectsForIdentity()` directly instead of fetching its own `GET /api/projects` — a Server Component fetching its own API is a round trip through HTTP to reach code it can call in-process. The route still exists for clients that are not the server. Mutations do go over HTTP, because that is where the ownership checks live.
- **The client boundary is one shell component, not the page.** `app/editor/page.tsx` stays a Server Component so it can read auth and the database; `components/editor/editor-home-shell.tsx` carries `"use client"` and holds only sidebar visibility and the dialog controller. Same shape spec 08's workspace needs.

- **`GET /api/projects` returns both lists**, `{ owned, shared }`, not a single flat list. Spec 06 says "the current user's projects" and spec 07 needs owned *and* shared from "the existing project data helper"; one shape satisfies both. `lib/projects.ts` is that helper and is the only reader — the route is a thin wrapper over it, so spec 07's Server Component can call `listProjectsForIdentity()` directly instead of fetching its own route.
- **`slug` is derived from the current name in the API response, never stored.** It matches `types/project.ts`'s `Project` exactly (`id`, `name`, `slug`, `role`), so wiring the sidebar in spec 07 is a swap of the data source and nothing else. This follows from the room-ID decision: the cuid is identity, the name is the label, the slug is a rendering of the label.
- **`/api/(.*)` is excluded from `auth.protect()` in `proxy.ts`.** Clerk's `protect()` answers a non-page request with `404` (`node_modules/@clerk/nextjs/dist/esm/server/protect.js`: page → redirect, Server Action → 401, everything else → `notFound()`), so with the middleware in front, every unauthenticated API call would have surfaced as a missing route instead of spec 06's required `401`. Each handler authenticates itself, which is also the migration target for the `createRouteMatcher` deprecation; the middleware keeps protecting page routes.
- **Ownership failures distinguish 404 from 403 by existence, not by visibility.** `findOwnedProject()` returns `not_found` for an unknown ID and `forbidden` for a real project owned by someone else, so a non-owner can confirm a project ID exists. Spec 06 mandates `403` for non-owner mutations, which requires exactly this; revisit if project IDs ever need to be unguessable.
- **Request validation is hand-rolled in `lib/project-input.ts` rather than using `zod`.** When specs 06–10 were built, `zod` was only a transitive dependency. Spec 21 declared `zod` 4.6.5; new validation uses it, and the `project-input.ts` parsers are covered by tests and stay until they need to change.

- `ProjectSidebar` is `position: fixed`, anchored `top-12` (matching the navbar's `h-12`) so it overlays the canvas below the navbar without pushing layout, per the "should not push page content" requirement.
- Auth route protection uses a protected-first `proxy.ts` strategy (block everything, allow-list `/`, `/sign-in(.*)`, `/sign-up(.*)`) rather than public-first, matching `architecture-context.md`'s "Only authenticated users can access protected routes" invariant and the spec's "Protect everything else by default." Narrowed in spec 06 to page routes only — see the `/api/(.*)` exclusion above.
- `/` owns its own redirect logic at the page level (Server Component + `auth()`) rather than relying on the proxy's default `auth.protect()` redirect, since the spec calls out `/`'s authenticated/unauthenticated behavior as a distinct requirement; `/` is in the proxy's public allow-list so this logic isn't shadowed.

- Project mutations flow through a single `ProjectDialogIntent` union (`create` / `rename` / `delete`) emitted by `useProjectDialogs`, rather than three separate callbacks. The editor currently hands it to `useMockProjects`; the persistence chapter swaps that one callback for an API call without touching the hook or any dialog.
- `slugify` lives in `lib/` rather than inside the create dialog, because `architecture-context.md` requires ownership/validation at the mutation boundary — the server will need to derive the identical slug from the same name.
- Sidebar row actions are inline hover/focus-revealed icon buttons instead of a dropdown menu: only two actions exist, it avoids a popup nested inside the sidebar overlay, and it needs no new `components/ui/*` file (protected per `ai-workflow-rules.md`). Tailwind v4 scopes `group-hover` behind `@media (hover:hover)`, so an explicit `@media (hover:none)` rule keeps the actions permanently visible on touch devices.
- Owner-only actions are gated inside `ProjectListItem` on `project.role === "owner"` rather than by which list rendered the row, so the rule holds wherever a project row is reused later.

- No headless browser tooling is installed, so the project dialogs were verified by build + prerendered-HTML grep + a compiled `slugify` check rather than by clicking through them. Dialog open/close, focus behavior, and the mobile scrim have not been exercised in a real browser.

- The Prisma schema is folder-based (`schema: "prisma"` in `prisma7.config.ts`), per the spec's `prisma/models/project.prisma` path. The generated client is written to `generated/prisma` at the repo root rather than inside `prisma/`, because a folder-based schema recursively globs `*.prisma` under the schema directory and generated output there can collide with schema discovery.
- Prisma 7 requires a driver adapter and does not read `.env*` files. `prisma7.config.ts` (the Prisma 7 filename; plain `prisma.config.ts` is the legacy name and is only searched as a fallback) loads `.env.local` then `.env` via `dotenv` so the CLI and the Next.js runtime resolve the same `DATABASE_URL` from one file.
- `lib/prisma.ts` validates its environment inside the client factory rather than returning a lazily-failing client, so a misconfigured environment fails at startup with a named error instead of surfacing as an opaque query failure inside a request handler. Since spec 21 the check is `getServerEnv()`.
- **The Liveblocks room ID is the `Project` cuid.** No `roomId` column, no slug-derived identifier. Spec 10 ("use the project ID as the Liveblocks room ID") and spec 07 ("the project ID and Liveblocks room ID should stay aligned") both point here; spec 07's other clause, "slugify the name to create the room ID", is the outlier and is not followed. The deciding factor is rename: spec 06 ships `PATCH /api/projects/[projectId]`, and a name-derived room ID makes rename either a lie (identifier frozen at creation, drifting from the name) or a distributed data migration (the canvas lives *inside* the Liveblocks room, which cannot be renamed in place — new room, copy storage, disconnect every client, strand every shared link). With the cuid, rename is one `UPDATE` on a text column. Identity (immutable cuid), label (mutable `name`), and locator (an optional future slug) stay separate. This is also the reversible direction: cuid → pretty URLs later is a nullable column plus a redirect, while slug → cuid would have to move canvas state between rooms. Consequences for spec 07: drop the "short unique suffix", drop the create dialog's room ID preview (a cuid cannot be previewed before insert), and keep spec 04's `slugPreview` only as a display label. Access resolution in specs 08 and 27 becomes a primary-key lookup.

- **Spec 21: Node 24 and `@types/node@^24`.** Vitest 5 requires Node 22.12+ and declares `@types/node` `^22 || >=24` as a peer, which conflicted with the old `@types/node@^20`. The local toolchain is Node 24, so `@types/node` moved to `^24` and CI pins Node 24.
- **Spec 21: Vite's native `resolve.tsconfigPaths` instead of `vite-tsconfig-paths`.** The spec names the plugin, but Vite 8 (under Vitest 5) resolves tsconfig paths itself and warns that the plugin is redundant. The plugin was uninstalled.
- **Spec 21: `getServerEnv()` still runs when `lib/prisma.ts` or `lib/liveblocks.ts` is first imported.** Both modules construct their client at module scope (`globalThis.x ?? createX()`), and the spec says to keep that construction exactly as it is. So `lib/env.ts` never validates on its own import, but importing either client module validates all four variables. `next build` passes because the build environment has them (locally from `.env.local`, in CI from secrets). If a later spec needs a route to import a client module without the full environment, make that construction lazy then.
- **Spec 22: `readErrorMessage` moved to `lib/error-message.ts`.** The spec says to reuse the share dialog's error pattern rather than invent a second one, so the helper `use-collaborators.ts` defined privately is now shared by both hooks.
- **Spec 22: "Edited 3h ago" is computed against the server's render time.** `app/editor/page.tsx` passes `now` as an ISO string down to `RecentProjects`, so the browser hydrates the same label the server sent. Dates older than five weeks print in UTC for the same reason. The labels do not tick while the page stays open.
- **Spec 22: the delete dialog links its error to the Delete button.** It has no input for `aria-describedby` to point from, and the button is the control the error is about.
- **Spec 23: `parseCanvasGraph` fills `generic` itself; it does not call `normalizeCanvasNode` first.** The spec wants a missing kind accepted and an unknown kind rejected at the boundary, but an unknown kind drawn as `generic` on the canvas. So the schema defaults a missing `kind`, and `normalizeCanvasNode`/`resolveNodeKind` are the lenient path for stored graphs. A caller that normalizes before parsing would let unknown kinds through, so boundary code parses the raw input.
- **Spec 23: migrated templates changed appearance.** Shape and color now come from the node kind, so the Microservices services are blue rectangles (the auth service a red hexagon) instead of differently colored pills, and the Event-Driven bus is an orange pill. The client-to-gateway edge's "HTTPS" label became the `http` protocol, which draws as "HTTP". The CI/CD template keeps its look through explicit overrides, because its nodes are pipeline steps that no kind describes.
- **Spec 23: the canvas node renderer imports `lib/canvas-schema.ts`, so zod is now in the workspace's client bundle.** The spec routes every reader through that module's normalization. Specs 24 and 41 need the validator on the client anyway.
- **Spec 23: an edge with a protocol and no label shows the protocol alone as its badge.** The spec only describes the prefix form. An unknown stored protocol shows no prefix. `EDGE_PROTOCOL_LABELS` and `EDGE_MODES` are additions the spec does not name; they keep display names and the mode list next to the IDs for spec 24's inspector.
- **Spec 21: `server-only` is aliased to its no-op `empty.js` in `vitest.config.mts`.** The package throws unless resolved with the `react-server` condition. Turning that condition on for all of Vitest would also switch React to its server build and break jsdom component tests, so only this one module is aliased.
- **Spec 24: selection comes from React Flow's `onSelectionChange` prop, not `useOnSelectionChange`.** The hook reads the React Flow store, and `CanvasFlow` renders `<ReactFlow>` itself with no `ReactFlowProvider` above it, so the hook cannot run where the selection state lives. The prop registers the same handler on the same store.
- **Spec 24: the inspector keeps keys away from the canvas with React Flow's `nokey` class instead of stopping propagation.** `deleteKeyCode` ignores any target inside `.nokey`, which covers buttons and the select triggers, not just inputs. The select popups render in a portal, so they carry the class on their own popup. `isEditableTarget` now honors `.nokey` as well, so the zoom keys follow the same rule.
- **Spec 24: an edge without a `mode` shows as Sync.** It draws as a solid line, so Sync is what it already is. Clicking Sync on such an edge writes nothing; clicking Async writes `mode: "async"`.
- **Spec 24: an unchanged draft writes nothing, measured against the value when typing began.** If a collaborator changes a field while you type and you end on the text you started from, their value stands. Clearing Technology or Description removes the key, so empty optional fields stay absent, the same as nodes that never had them.
- **Spec 24: "Apply kind style" is disabled when the node already has the kind's shape and color.** The spec only says the button restyles. Disabling it when it would do nothing shows that the style is already applied.
